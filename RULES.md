# RULES

Этот файл задает рабочие правила для людей и ИИ-агентов в `word-cards-admin`.
Его цель: сократить лишние обходы по проекту, ускорить типовые изменения и сохранить предсказуемый стиль кода.

Современный принцип для таких файлов простой:
- писать только то, что агент не может надежно вывести сам из кода
- держать правила короткими, операционными и проверяемыми
- не превращать файл в учебник или дублирование всего проекта

## 1. Как принимать решения

Приоритет такой:
1. Ближайший рабочий паттерн рядом с изменяемой фичей.
2. Общие переиспользуемые слои проекта: `shared`, `entities`, `features`, `widgets`.
3. Правила из этого файла.
4. Новая абстракция только если без нее уже начинается заметное дублирование.

Главная цель:
- минимальный diff
- локальное изменение
- код, который выглядит так, будто всегда был частью проекта

## 2. Быстрый маршрут по проекту

Перед тем как писать новый код, сначала проверь:
- `src/shared/` — базовые UI-компоненты, hooks, api, lib, config
- `src/pages/` — готовые экранные паттерны
- `src/features/` — пользовательские сценарии и локальные фичи
- `src/widgets/` — крупные составные блоки
- `src/entities/` — сущности и связанный с ними API
- `src/assets/styles/colors.scss` — палитра проекта

Импортируй через path aliases:
- `@shared/*`
- `@features/*`
- `@entities/*`
- `@pages/*`
- `@widgets/*`
- `@assets/*`

## 3. Куда класть код

- `pages` — страницы и их локальный UI
- `widgets` — крупные блоки, которые собирают несколько частей интерфейса
- `features` — законченное пользовательское действие или сценарий
- `entities` — доменная сущность, ее типы и связанный API
- `shared` — универсальный UI, hooks, утилиты, базовые API-инструменты

Не поднимай код выше по слоям без причины.
Если логика нужна только одной странице или одной модалке, держи ее рядом.

## 4. Обязательные правила кода

### TypeScript

- Использовать только `const`. `let` запрещен полностью — это правило проверяется линтером (`no-restricted-syntax` в `eslint.config.js` запрещает `VariableDeclaration[kind="let"]` как ошибку). Если значение должно меняться, выносите логику в функцию, используйте `reduce`/immutable-обновление состояния или разбивайте вычисление на отдельные `const`.
- `any` запрещен.
- Если тип неочевиден, опиши его явно или переиспользуй существующий.

### React

- Используй существующие компоненты, если они уже решают похожую задачу.
- Не объявляй функции прямо в JSX. Выноси их в тело компонента.
- Разрешено использовать `map` прямо в JSX для рендера списков, если внутри нет новой бизнес-логики.
- Не храни JSX в переменных без явной причины.
- Если компонент разрастается, выделяй смысловые части в соседние файлы.

### Memoization policy

- Следуй текущему стилю проекта: значения и обработчики, зависящие от состояния и пропсов, обычно стабилизируются через `useMemo` и `useCallback`.
- JSX, JSX-узлы и простые элементы списка дополнительно мемоизировать не нужно.
- Inline style object в JSX не писать. Статические стили держать в `*.module.scss`, вычисляемые значения — выносить отдельно.

### Стили и UI

- Сохраняй существующий визуальный язык проекта.
- Используй цвета из `src/assets/styles/colors.scss`.
- Если нужного цвета нет, добавляй его централизованно, а не локально в модуле.
- Для компонентов использовать соседние `*.module.scss`.
- Соблюдай семантику верстки и аккуратную структуру JSX.

### Текст и локализация

- UI-текст по умолчанию писать на русском языке.
- Если файл уже использует русские строки в конкретной кодировке, не меняй это поведение без причины.

## 5. Порядок внутри компонента

Если в компоненте используются эти группы, ориентируйся на такой порядок:
1. `useNavigation`
2. `useRoutes`
3. `useActions`
4. `useAppDispatch`
5. `useAppSelector`
6. `useState`
7. query hooks / API hooks
8. custom hooks
9. `useMemo`
10. `useCallback`
11. `useEffect`

Если часть пунктов не используется, просто пропускай их.

## 6. Правило ответственности

Компонент должен нести свою прикладную логику, если она относится именно к нему.

Пример:
- модалка удаления должна содержать логику удаления, если она нужна только ей
- не раздувай родителя техническими пропсами и промежуточными обработчиками

Выносить выше можно только то, что реально переиспользуется или является общей orchestration-логикой.

## 7. Как работать агенту без лишних блужданий

Перед реализацией:
1. Найди ближайший похожий файл.
2. Проверь, нет ли уже готового компонента, цвета, хука, запроса или модалки.
3. Повтори существующий паттерн, а не придумывай новый.

Во время реализации:
1. Делай локальные изменения.
2. Не запускай широкий рефакторинг без прямой необходимости.
3. Не создавай новые сущности и слои, если задачу можно решить в текущей структуре.

После реализации:
1. Проверь визуальную и архитектурную согласованность с соседним кодом.
2. Запусти релевантные проверки.

## 8. Проверки перед завершением

Используй:
- `npm run lint`
- `npm run build`

Если менялась только локальная UI-логика, достаточно сначала `npm run lint`.
Если затронуты типы, импорты, сборка страниц или API-связи, дополнительно запускать `npm run build`.

## 9. Антипаттерны

Не делать без необходимости:
- новый базовый UI-компонент, если уже есть похожий в `shared`
- новый цвет вне общей палитры
- inline-функции в JSX
- inline style objects в JSX
- `any`
- `let` (используйте `const`; см. §4 TypeScript)
- крупный монолитный компонент
- перенос локальной логики в родителя только ради формального контроля сверху
- абстракцию "на будущее", если сейчас у нее нет второго реального применения

## 10. Критерий хорошего изменения

Хорошее изменение в этом проекте:
- похоже на существующий код
- лежит в правильном слое
- минимально по объему
- читается человеком без дополнительных пояснений
- не заставляет следующего агента заново выяснять, "как тут принято"
